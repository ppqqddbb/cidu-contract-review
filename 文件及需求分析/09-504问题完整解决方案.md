# 504 超时问题完整解决方案

## 问题现象

- **直接在 Dify 界面调用**：正常工作 ✓
- **通过应用调用 Dify API**：HTTP 504 Gateway Time-out ✗
- **错误来源**：nginx/1.29.1（Dify 服务器的网关）

## 根本原因

504 错误由 **Nginx 网关** 返回，说明问题发生在 Dify 服务器端，而不是客户端。主要原因：

1. **Nginx 代理超时限制**：默认 `proxy_read_timeout` 通常只有 60 秒
2. **AI 处理时间过长**：合同智审需要 3-10 分钟
3. **blocking 模式的限制**：应用使用阻塞等待模式，容易超时

## 解决方案

### 方案一：客户端超时增加（已完成）✓

**已修改文件**：`services/api/app/main.py`

```python
# 第 204-206 行
timeout = httpx.Timeout(600.0, connect=30.0, read=600.0, write=60.0)
```

**作用**：确保客户端愿意等待足够长的时间

**局限性**：如果 Dify 服务器的 Nginx 超时更短，客户端等待再久也没用

### 方案二：使用流式响应（已实现）⭐⭐⭐

**核心改进**：将 Dify 调用从 blocking 模式改为 streaming 模式

#### 实现架构

```python
_dify_chat()  # 主入口
    ├─> _dify_chat_streaming()  # 优先使用流式模式
    └─> _dify_chat_blocking()   # 失败后回退到阻塞模式
```

#### 流式模式的优势

1. **不会超时**：持续接收数据流，Nginx 不会认为连接空闲
2. **实时响应**：可以看到 AI 生成的过程（未来可用于进度显示）
3. **更可靠**：与 Dify 界面使用相同的机制
4. **自动降级**：流式失败会自动回退到阻塞模式

#### 关键代码

```python
async with client.stream(
    "POST",
    f"{DIFY_BASE_URL}/chat-messages",
    json={
        "response_mode": "streaming",  # 关键：使用流式模式
        ...
    },
) as response:
    async for line in response.aiter_lines():
        if line.startswith("data: "):
            data = json.loads(line[6:])
            if data.get("event") == "message":
                full_answer += data.get("answer", "")
```

### 方案三：Dify 服务器 Nginx 配置调整（建议）⚙️

**需要在 Dify 服务器上修改 Nginx 配置**

找到 Dify 的 Nginx 配置文件（通常在 `/etc/nginx/sites-available/` 或 `/etc/nginx/conf.d/`）：

```nginx
server {
    listen 80;
    server_name ciduai.daneng.cc;

    location /v1/ {
        proxy_pass http://dify_backend;
        
        # 关键配置：增加代理超时时间
        proxy_connect_timeout 30s;
        proxy_send_timeout 120s;
        proxy_read_timeout 600s;  # 从默认60s增加到600s（10分钟）
        
        # 保持长连接
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        
        # 增加缓冲区大小，处理大文件
        proxy_buffer_size 16k;
        proxy_buffers 4 64k;
        proxy_busy_buffers_size 128k;
        
        # 其他必要的头部
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

**重启 Nginx**：
```bash
sudo nginx -t  # 测试配置
sudo systemctl reload nginx  # 重新加载配置
```

## 为什么直接在 Dify 界面可以正常使用？

因为 Dify 界面使用的是 **流式响应（SSE）**，而之前你的应用使用的是 **阻塞模式**：

| 模式 | Dify 界面 | 之前的应用 | 现在的应用 |
|------|----------|-----------|-----------|
| 响应方式 | streaming | blocking | streaming + blocking（降级） |
| 是否持续接收数据 | ✓ 是 | ✗ 否，一次性等待 | ✓ 是 |
| Nginx 是否认为超时 | ✗ 否 | ✓ 是（60秒无数据） | ✗ 否 |

## 常见问题 FAQ

### Q1: 为什么要保留阻塞模式？

**A**: 作为降级方案。如果流式模式因为网络问题失败，阻塞模式可以作为备用。

### Q2: 流式模式会影响性能吗？

**A**: 不会。流式模式反而更高效，因为：
- 减少了内存占用（不需要一次性缓存完整响应）
- 降低了超时风险
- 提供了更好的用户体验（未来可显示进度）

### Q3: 如果 Dify 服务器的 Nginx 超时很短怎么办？

**A**: 流式模式可以避免这个问题，因为持续的数据流会让 Nginx 认为连接是活跃的。但如果仍有问题，需要联系 Dify 服务器管理员调整 Nginx 配置（见方案三）。

### Q4: 可以强制使用阻塞模式吗？

**A**: 可以。直接调用 `_dify_chat_blocking()` 函数，或者修改 `_dify_chat()` 函数跳过流式尝试。
